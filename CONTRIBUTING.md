# Contributing

Thanks for helping make ripbi better. ripbi is a static analysis, linting, and
tree-shaking tool for Power BI semantic models and DAX — the
[README](README.md) covers what it does; this file covers how to work on it.

This guide deliberately does not restate architecture. [AGENTS.md](AGENTS.md)
is the routing table: it points into the per-crate `CONTEXT.MD` files, which
point further down into topic docs. Start there when you need to know where a
change belongs.

AI agents are first-class contributors in this repo. If you are one, read
[AGENTS.md](AGENTS.md) and follow its routing and coding standards exactly,
like any human contributor.

## Dev setup

You need [Rust](https://rustup.rs/) stable. The workspace is on edition 2024,
so 1.85 or newer; there is no MSRV and CI tracks stable.

```sh
git clone https://github.com/bgarcevic/ripbi.git
cd ripbi
cargo build --workspace
```

Development works on Linux, macOS, and Windows — CI runs the test suite on all
three. To see the tool do its thing:

```sh
cargo run -p ripbi -- scan "samples/AdventureWorks Sales.pbip"
```

## Local CI parity

CI is the definition of done: if these pass locally, your PR will pass CI.

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features --locked
cargo test --workspace
```

The `cargo doc` step exists because broken intra-doc links are only caught by
rustdoc — clippy and the test suite never see them. On PowerShell, set the
variable first instead of prefixing: `$env:RUSTDOCFLAGS='-D warnings'`.

Lint levels live in the root `Cargo.toml` under `[workspace.lints]`, so a
plain local `cargo clippy` already denies what CI denies.

## Where things live

The main crates:

- [`crates/ripbi-core`](crates/ripbi-core) — the pure library: format
  ingestion, DAX lexing, graph reachability. It never prints and never exits.
- [`crates/ripbi-app`](crates/ripbi-app) — the front-end neutral app layer:
  discovery, config, and the `scan`/`report`/`deps` pipelines as typed results.
  It never prints either.
- [`crates/ripbi-cli`](crates/ripbi-cli) — the `ripbi` binary: a thin
  orchestration layer over `ripbi-app`. All printing lives here.

The experimental [egui desktop app](desktop-egui/README.md) lives in
`desktop-egui/`, a standalone Cargo package over `ripbi-app`. It is excluded
from workspace builds and CI.

For anything deeper, follow the routing: [AGENTS.md](AGENTS.md) →
[crates/ripbi-core/CONTEXT.MD](crates/ripbi-core/CONTEXT.MD) and
[crates/ripbi-cli/CONTEXT.MD](crates/ripbi-cli/CONTEXT.MD) → the topic docs
they point to.

## Docs site

The user guide (https://bgarcevic.github.io/ripbi/) is an mdBook built by
`.github/workflows/pages.yml`. Its source, `book/src/`, is generated by
`book/assemble.sh` from the canonical docs that live next to the code — never
edit or link into `book/src/`; change the canonical doc, or one of the
hand-written pages under `book/manual/`. To preview the assembled book
locally:

```sh
cargo install mdbook --version 0.4.52 --locked
cargo install mdbook-linkcheck --locked
book/assemble.sh && mdbook serve book
```

Install the mdBook version pinned in `.github/workflows/pages.yml` — mdBook
0.5 changed the backend protocol, so a newer mdbook breaks the link checker
with "Unable to parse RenderContext". The Pages workflow builds the book on
every PR that touches docs, and a broken internal link fails that build.

The terminal recordings in `docs/media/` (used by the README and the user
guide) are animated SVGs generated from real runs against the samples. When a
change alters a recorded command's output, regenerate them:

```sh
python scripts/record_demos.py
```

It builds a release binary, replays each demo in a throwaway git repository,
and rewrites the SVGs; the output is byte-stable, so an unchanged recording
produces no diff.

## Contribution norms

**Tests for behavior changes.** Unit tests live inline as `#[cfg(test)]`
modules; integration tests live in each crate's `tests/` directory with
fixtures and golden baselines (`crates/ripbi-cli/tests/fixtures/` holds the
AdventureWorks baseline). A parser or output change without a fixture update
is probably not done.

**The standards that bite.** Two of [AGENTS.md](AGENTS.md#coding-standards)'s
coding standards come up in almost every change: `ripbi-core` never prints to
stdout/stderr and never calls `std::process::exit` (the CLI owns all I/O), and
JSON traversal must tolerate schema drift — never panic or assume on unknown
or missing fields. Read all five before your first PR.

**Good issues** include a minimal reproduction (a small `.pbip`/TMDL snippet,
or steps against a `samples/` project), expected vs. actual behavior, and the
output of `ripbi --version`.

## Samples

The projects under [`samples/`](samples/) are Microsoft's own sample projects,
redistributed under MIT and attributed in [samples/README.md](samples/README.md).
They are not covered by ripbi's license. Never modify or relicense them, and
don't add new test fixtures there — fixtures belong with the crate that uses
them.

## Commits and PRs

- PRs are squash-merged, so the **PR title** becomes the commit subject on
  `main`. Write it as a [Conventional Commit](https://www.conventionalcommits.org/)
  in the imperative mood: `feat(scan): add --queries-from`,
  `fix(tmdl): keep columns named in partition M`, `docs: …`. Allowed types:
  `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`,
  `revert`, `style`. The `pr checks` workflow enforces this, because the title
  decides the next version (see [Versioning](#versioning)).
- Add an entry under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md) for any
  change users can see: it becomes the release notes. PRs that touch shipped
  code (`crates/*/src`, the GitHub Action, the Azure Pipelines
  template) without one fail the check; a maintainer adds the `skip-changelog`
  label for changes users cannot see.
- No AI attribution: PR descriptions and commits must not carry
  `Co-authored-by: … <noreply@anthropic.com>` trailers or "Generated with
  Claude Code" footers. The check rejects them, and the project's
  `.claude/settings.json` turns them off for Claude Code sessions.
- Reference the issue in the PR description ("Closes #41").
- Keep PRs small and focused — one change per PR.
- Don't bump versions in your PR: releases are automated (below).

## Releases

Releases are automated by `.github/workflows/release-pr.yml` and
`release.yml`:

- A bot keeps one `chore(release): prepare X.Y.Z` PR open from the
  `release/next` branch, rebuilt on every merge to `main`. It moves
  `[Unreleased]` into a dated `[X.Y.Z]` section and bumps every version file
  (`python scripts/sync_version.py --set X.Y.Z`). With nothing under
  `[Unreleased]`, there is no release PR.
- Polish the notes by editing `CHANGELOG.md` on that PR just before merging;
  the next merge to `main` rebuilds the branch and drops edits made there.
- Merging it tags `vX.Y.Z` and starts `release.yml`: the CLI archives (each
  run once on its native runner first), one
  GitHub release whose body is the changelog section, then the GitHub Action
  mirror and crates.io.

### Versioning

The bump comes from the PR titles since the last release: `feat` is a minor,
everything else a patch, and `!` after the type (`feat!:`) or a
`BREAKING CHANGE:` line in the body a major. Breaking PRs need the
`breaking-approved` label. While the major version is 0, breaking changes bump
the minor instead.

A `Release-As: X.Y.Z` line in a commit body since the last release overrides
the computed version (the newest wins): use it in a squash-merge message for a
deliberate 1.0.0, or when the titles undersell a release.

### Version metadata

Every crate and the CLI archives share one version and tag.
The source of truth is `[workspace.package].version` in the root `Cargo.toml`.
`python scripts/sync_version.py --write` (Python 3.11+) propagates it to the
workspace dependency requirements, the local package versions in `Cargo.lock`,
and the pinned
install examples in `book/manual/installation.md`; `--set X.Y.Z` changes the
workspace version first. Third-party dependency versions stay unchanged. CI
rejects drift, and the release checks the tag against it before building.

To release by hand (a release candidate, or if the bot is unavailable): run
`--set`, cut the changelog section, merge, then push the `vX.Y.Z` tag
yourself. A tag pushed by hand starts `release.yml` directly.
